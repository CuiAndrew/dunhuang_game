# 敦煌逃亡：可行性研究与技术计划

## 结论

项目可行，适合采用“无构建工具、静态服务器启动、程序化美术”的 MVP 路线。Three.js r169、原生 ES Modules、CanvasTexture、Web Audio 和 DOM HUD 可以覆盖提示词与架构图中的核心玩法；主要工程风险集中在无限轨道回收、移动端性能和浏览器音频权限，而不是 API 可用性。

当前实现将 Three.js 固定为 CDN import map 的 `0.169.0` 版本，运行时不需要构建工具或本地打包；`package.json` 中的开发依赖仅用于 Node 单元测试和长跑模拟。这样保留原生模块架构，静态服务器即可启动。

## 技术可行性

| 领域 | 方案 | 风险与对策 |
| --- | --- | --- |
| 轨道 | 弧长参数 `s` + 采样点 `position/forward/right` | 所有实体共用 `evalTrack`，避免弯道坐标漂移 |
| 无限世界 | 轨道环、障碍池、装饰 `ChunkPool` | 按 `s` 回收，限制池容量，禁止运行中无限增长 |
| 操作 | 键盘、触摸、鼠标统一成 LEFT/RIGHT/JUMP/SLIDE/PAUSE | 输入缓冲、coyote time 与边界回弹改善容错 |
| 碰撞 | `s/lane/y` 的确定性判定 | 20% 宽容；物理障碍组至少留一条车道，GAP 组全车道占用但要求跳跃 |
| 美术 | CanvasTexture、几何体、固定色板 | 无 png/glb/mp3 外部资源；动态对象预热 |
| 音频 | Web Audio 合成音效与五声音阶循环 | 首次交互后 resume；不支持 Web Audio 时静默降级 |
| 性能 | 固定步长、低对象数、阴影/装饰自适应降级 | 45 FPS 持续 3 秒时依次降低像素比、阴影尺寸并减少装饰密度；真机发布前仍需实测 |

## 交付路线

1. **核心可玩闭环**：固定步长循环、状态机、轨道推进、三车道动作、相机跟随。
2. **玩法系统**：障碍生成与碰撞、追兵距离、硬币、磁铁/护盾/加速、分数与最高分。
3. **表现层**：敦煌色板、程序纹理、道路标线、追兵/道具/粒子、HUD、菜单、暂停与结算。
4. **工程化验收**：对象池重置、标签页自动暂停、CDN 版本锁定、无音频降级、自动化测试和浏览器冒烟验证。
5. **后续增强**：补充真实桌面/移动设备 FPS、draw call、三角面和内存趋势记录，并继续丰富环境构件与视觉细节。

## 验收标准

- `npm test` 全部通过。
- 静态服务器打开后可见开始界面，点击后进入 PLAYING，HUD 距离持续增长。
- 暂停按钮显示暂停层，重新开始清空跑局数据并重置对象池。
- 运行中无外部二进制美术资源依赖；Three.js 来源为锁定的 CDN r169 import map。
- 浏览器不支持 Web Audio 时游戏仍可开始，音频仅静默降级。
